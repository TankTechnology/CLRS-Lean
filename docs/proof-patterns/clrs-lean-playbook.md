For the chapters not yet started, we use a three-layer approach of "specification layer → implementation layer → proof layer":

1. **Specification layer**: first define mathematical predicates such as the vertex/edge set of a graph, paths, cuts, and flow.
2. **Implementation layer**: write executable algorithm functions (Union-Find, BFS/DFS, Dijkstra/Bellman-Ford, Floyd-Warshall, Edmonds-Karp, etc.).
3. **Proof layer**: prove that the algorithms satisfy the specification (connectivity, shortest paths, max-flow = min-cut, etc.).

## 2. Core Design Principles

### 2.1 Separate Specification from Implementation

- Use `Prop` predicates to describe "what should hold":
  - Sorting: `Sorted`, `Permuted`
  - Trees: `InTree`, `RedBlackShape`, `NoRedRed`, `BalancedBlackHeight`
  - Graphs: paths, cuts, flow values
- Implement the algorithms as executable Lean functions.
- Theorems connect the two: `algorithm input` satisfies `Spec`.

### 2.2 Prefer Invariants over Complex Types

Don't cram all constraints into a single inductive type.
For instance, Chapter 13's `WeakRB` combines three shapes with `∨`, which is easier to prove about than defining a complex indexed family.

### 2.3 Local First, Then Combine

- Split the algorithm into symmetric local cases (e.g., the red-black tree's left-left / left-right / right-left / right-right).
- Prove a small theorem for each local case separately.
- Finally wrap them up with a dispatcher/composition theorem.
- **Don't abstract too early**: just write three similar lemmas three times, and only extract shared utilities once at least two chapters need them.

## 3. Lean Tactic Cheat Sheet

### 3.1 Everyday Go-To Tactics

| Tactic | Purpose | Example |
|---|---|---|
| `simp [a, b, c]` | unfold/simplify with explicit lemmas | `simp [RedBlackShape, NoRedRed]` |
| `omega` | Nat/int inequalities, heights, indices | height equalities, branch-size bounds |
| `linarith` | chains of linear inequalities | cost upper bounds, nonnegative potential |
| `rcases` | destructure `∧`, `∨`, `∃`, product types | `rcases h with ⟨h1, h2⟩` |
| `cases t` / `cases c` | case split on inductive types like trees/colors | `cases c with \| black \| red` |
| `split` | handle branches and negative hypotheses generated by `match` | `balanceLeft`'s impossible branch |

### 3.2 Handling `match` Impossible Branches

After using `split` on a function with a default branch (e.g., `balanceLeft`), Lean generates a negative hypothesis:

```lean
hneg : ∀ a b c x y, ¬ (l = node red (node red a x b) y c)
```

Handling pattern:

```lean
exfalso
apply hneg a b c x y; rfl
```

### 3.3 Limits of Automation

- `aesop` / `tauto`: good for trivial propositional combinations, but the key branches still need a manual `rcases`.
- `ring` / `norm_num` / `positivity`: algebraic simplification and positivity proofs.
- `omega` is most effective for `Nat` heights; when reals/logs come into play, fall back to `linarith` or `gcongr`.

### 3.4 Controlling `simp`

- Prefer `simp [lemma1, lemma2]`; avoid bare `simp`, which gets slow in large files.
- If `simp` unfolds the goal too aggressively, switch to `simp only [MyDef]` or a manual `unfold MyDef`.
- Once the proof is stable, you may set up a local `attribute [simp]` collection, but don't casually add `@[simp]` to global definitions.

## 4. Common Proof Patterns

This section is a short cheat sheet; for a cross-chapter overview of "geometric shapes" see
[`geometric-proof-patterns.md`](geometric-proof-patterns.md). The lightweight
Lean skeletons extracted so far live in `CLRSLean/ProofPatterns/`.

### 4.1 Sorting Algorithms

1. `Sorted`: induct on the definition.
2. `Permuted` / membership: usually via `List.Perm` or an `InTree`/`InList` equivalence.
3. Loop invariant: write the `LoopInvariant` predicate first, then prove initialization, preservation, and termination.

### 4.2 Recursive Data Structures (Trees, Heaps)

1. The recursive structure of the theorem should align with the function definition.
2. On a tree, `cases t` makes the subtree hypotheses serve directly as `ih`.
3. Balance/height properties usually need auxiliary lemmas such as `blackHeight_rotateLeft`.

### 4.3 Greedy Algorithms

1. **Exchange argument**: prove that any optimal solution can be transformed step by step into the greedy solution without getting worse.
2. Commonly use the two lemmas `GreedyChoiceSafe` + `OptimalSubstructure`.

### 4.4 Graph Algorithms

1. **Invariant**: e.g., Dijkstra's "settled set has shortest distances to the source".
2. **Cut/path certificates**: prove that some edge is a light edge, or that some path exists.
3. **Exchange lemma**: in MST proofs, swap non-greedy edges into the optimal solution.

### 4.5 Amortized Analysis

1. Define a `potential` function.
2. Prove `potential` is nonnegative and telescopes.
3. For each operation, prove `actual cost + Δpotential ≤ amortized cost`.

### 4.6 Functional Graph Search (BFS / DFS)

Chapter 22's BFS/DFS uses a functional model of **fuel + `Finset.toList`**:

- Bound the recursive search with `fuel : Nat`, avoiding reliance on Lean's termination checker on unstructured graphs.
- `Finset.toList` makes the traversal order noncomputational (`noncomputable`), yet Lean's inductive proofs still apply.
- Represent the state (colors, discovery/finish times, parent) with a record + functions; for updates that change only one field, write a `@[simp]` lemma per field, e.g.:
  - `setColor_color`, `setDiscovery_color`, `setFinish_color`, `setParent_color`.
- When `dfsVisit` processes the adjacency list, it visits neighbors in order with `List.foldl`. When proving foldl invariants:
  1. Name `foldl`'s step function with `let step := ...` to make rewriting convenient.
  2. On the list, use `induction vs generalizing s0`; the induction hypothesis is then already "for an arbitrary accumulator".
  3. Using the definition of `List.foldl`, rewrite the `v :: vs` case as `foldl step (step s0 v) vs`, then handle the `if color v = white` inside `step` with `by_cases`.
- Experience with DFS color invariants ("introduce no new gray vertices"):
  - Do the fuel induction on a fixed vertex `w` instead of generalizing `w` too; then the outer IH is directly about `w`, and you don't need to re-instantiate `w` in the foldl sublemma.
  - First prove the invariant for a single step of `dfsVisit`, then prove that `dfsFromList` preserves "no gray" and "all vertices become black".

## 5. File and Module Conventions

### 5.1 Directory Layout

```
CLRSLean/
  Chapter_XX.lean                 # chapter guide + namespace
  Chapter_XX/
    Section_XX_Y_Short_Name.lean  # specific section
Tests/
  Chapter_XX_Interface.lean       # optional public API check
```

### 5.2 Module Doc Conventions

- Use `/-! # Chapter/Section Title -/` at the top of the module.
- Don't use `##` for inner section comments — doc-gen may complain about header nesting errors; use `/-! **Section Title** -/` instead.
- Use the `{name}` or `{lit}` roles for inline code references:
  - `{name}`RBTree.insert``: references a Lean definition/theorem.
  - `{lit}`RB-INSERT-FIXUP``: literal text that is not a Lean identifier.

### 5.3 Status Words

Use a fixed set of words for chapter/theorem status:

- `proved`
- `partial`
- `statement`
- `blocked-design`
- `blocked-mathlib`
- `deferred-implementation`
- `future-work`
- `out-of-scope`
